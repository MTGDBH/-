# 智能管家接入 N-of-1 个体干预闭环

## 新增工具

- `propose_intervention`：只生成版本化确认预览，不创建干预；要求明确意图、目标指标、可追溯且已审核证据、可执行复测方式、非药物且非急症。
- `list_active_interventions`：读取当前老人处于 `active` 或 `evaluating` 的干预。
- `record_adherence`：本人或已授权家属生成执行记录确认预览；确认后调用干预专用 executions API。
- `evaluate_intervention`：仅老人本人可显式启动，调用独立 Python 评价引擎并保存版本化结果。
- `explain_intervention_result`：确定性区分测量值、模型预测、描述性变化、个体证据等级、数据不足和混杂因素。

所有工具调用均写入 `agent_tool_calls`，保存参数、对象绑定、工具版本、结果哈希、证据快照、失败原因、耗时和状态。

## 编排流程

```text
用户消息
  ├─ 急症规则命中 → 中止普通工具 → 急救建议
  └─ 非急症
      ├─ 明确提出干预 → 安全/证据/指标/复测门槛
      │   └─ confirmation_preview → 前端完整确认卡
      │       ├─ 拒绝 → 不创建干预
      │       └─ 本人确认 → 创建 pending_confirmation → 专用 API 激活
      ├─ 明确报告执行 → adherence_preview → 确认后追加执行日志
      ├─ 复测数据 → 既有 followup 匹配与结果确认
      ├─ 明确评价 → Python N-of-1 引擎 → 保存版本化结果
      └─ 解释结果 → 五类信息分栏、安全中文结论
```

V3 对话状态新增 `intervention_stage`，保留 proposal/adherence/evaluated/explained 阶段。干预回合由确定性回复渲染工具结果，不允许 LLM 改写确认门槛；无 LLM 时使用同一路径。

## 安全门槛

1. 只有老人本人可以提议确认和启动评价；家属只能在有效照护关系下查看和协助记录执行，医生保持授权只读，管理员不默认读取个人干预。
2. 提议必须同时具备：明确请求、目标指标、当前基线测量、审核通过且可追溯的证据、同条件复测方法、非药物行为和停止就医条件。
3. 胸痛、呼吸困难、意识异常、卒中样症状、抽搐或大量出血直接进入急症规则，跳过干预工具。
4. 停换药、增减药、剂量和替代就医内容在工具与既有干预契约两层拦截。
5. 创建干预前必须展示“做什么、做多久、如何记录、何时复测、观察指标、理由、证据来源、停止并就医”卡片。提议工具自身不写 `interventions`。
6. 输出后处理禁止确定性疗效、停药、替代医生或保证降低风险的表述。
7. 数据不足时评价契约的变化量、效应量和区间为空，不产生效果结论。

## 对话示例

用户：“请帮我制定一个观察血糖的饭后散步干预方案，做14天。”

智能管家：读取当前血糖记录与审核证据，返回完整确认卡；此时数据库中没有新干预。用户点击“确认创建干预”后，前端才调用专用创建与本人确认接口。

用户：“我今天完成了散步干预，请记录。”

智能管家：返回“本次已完成”的执行预览。确认后追加执行日志；家属协助时数据来源固定为 `caregiver_report`。

用户：“请评估这个干预的效果。”

智能管家：仅在干预为 `evaluating` 时运行独立评价引擎；随后解释实测基线/结局、是否使用预测、描述性变化、个人证据等级、bootstrap 区间、混杂和安全方向。

用户：“我想做干预，但现在突然胸痛、喘不过气。”

智能管家：不调用普通干预工具，直接建议立即联系急救并由身边人员陪同，不等待模型分析。

## 向后兼容

- 保留 V2/V3 原工具名、最大三工具预算、Curve→GraphRAG 证据链、普通行动 API、复测 followup 语义和旧前端卡片。
- N-of-1 创建/确认/拒绝/执行继续走 `/api/actions/interventions` 专用子路由；通用 `/api/actions/:id/confirm` 仍拒绝处理干预，避免旧入口绕过专用状态机。
- 数据库升级仅使用 `CREATE TABLE IF NOT EXISTS` 和 `addColumnIfMissing`，旧库原位兼容。
- 原有趋势、风险、知识、设备、预警、健康摘要和复测工具行为未改变；仅在识别到干预意图时走新增确定性分支。
